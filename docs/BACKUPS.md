# دليل النسخ الاحتياطي واستعادة البيانات (Backup & Disaster Recovery Runbook)

يوضح هذا الدليل معمارية النسخ الاحتياطي الآلي المشفر، وسياسة الاحتفاظ والتخزين متعددة الطبقات (3-2-1 Backup Strategy)، وكيفية إجراء تدريبات الاستعادة الدورية (Restore Drills) في بيئة معزولة بأمان تام دون أي تأثير على بيئة الإنتاج.

---

## 1. آلية النسخ الاحتياطي والتحقق الآلي (Automated Backup & Verification)

يعمل سير العمل الآلي في GitHub Actions (`.github/workflows/backup.yml`) وفق المعايير التالية:
- **الجدولة والتوقيت**: يعمل تلقائياً كل يوم أحد الساعة `02:00` صباحاً بتوقيت UTC، بالإضافة إلى إمكانية التشغيل اليدوي الفوري (`workflow_dispatch`).
- **تصدير البيانات**: يتم استخراج البيانات ومخطط الجداول عبر `pg_dump` باستخدام بروتوكول Session Pooler الخاص بـ Supabase.
- **التشفير المتماثل القوي**: يُشفّر ملف الـ SQL فورياً بخوارزمية `AES256` عبر أداة `gpg` باستخدام كلمة مرور سرية معقدة (`BACKUP_PASSPHRASE`).
- **التحقق الآلي ثنائي المراحل (Two-Phase Verification)**:
  1. **التحقق من ملف التصدير والتشفير**: يتأكد سير العمل من أن ملف التصدير غير فارغ ويحتوي على ترويسة PostgreSQL القياسية، ثم يتأكد من إنشاء الملف المشفر بنجاح وحذف ملف الـ SQL غير المشفر فوراً.
  2. **اختبار فك التشفير والاستعادة الآلي (Automated Restore Drill)**: يقوم الـ Action بفك تشفير الملف تجريبياً، ثم استعادته داخل حاوية PostgreSQL معزولة ومؤقتة (`ephemeral-postgres:16-alpine` على منفذ 5433)، ويتأكد من إنشاء الجداول وقراءة عدد الصفوف بنجاح قبل رفع الـ Artifact، ثم يمحو ملف الـ SQL المفكوك فوراً.
- **الأسرار المطلوبة في المستودع (GitHub Secrets)**:
  - `SUPABASE_DB_URL`: سلسلة اتصال قاعدة البيانات (`postgres://postgres.[ref]:[password]@aws-0-[region].pooler.supabase.com:5432/postgres`).
  - `BACKUP_PASSPHRASE`: كلمة مرور قوية ومعقدة (لا تقل عن 32 حرفاً عشوائياً) تُستخدم حصرياً لتشفير وفك تشفير النسخ الاحتياطية.

## 2. مراجعة سياسة الاحتفاظ والتخزين (Retention & Storage Policy)

### لماذا فترة الـ 30 يوماً السابقة غير كافية؟
- **طبيعة النشاط الطلابي**: تعتمد أنشطة إيناكوس قنا على دورة موسمية سنوية تمتد من شهر سبتمبر وحتى شهر أغسطس من العام التالي، ويتم ترحيل البيانات وتصفية الحسابات وإصدار تقارير الرعاة بعد انتهاء المسابقة الوطنية.
- **الحذف التلقائي من GitHub**: تقوم منصة GitHub بحذف الـ Artifacts نهائياً وبلا رجعة بعد انتهاء مدة الاحتفاظ المحددة. في حال وقوع أي تلف صامت في البيانات أو الرغبة في مراجعة أرشيف مالي لموسم سابق بعد مرور أكثر من شهر، ستكون كافة النسخ قد حُذفت تماماً إذا اقتصر النظام على 30 يوماً فقط داخل GitHub.

### سياسة التخزين والاحتفاظ المعتمدة (3-Tier 3-2-1 Retention Policy):

| الطبقة (Tier) | وسيط التخزين (Storage Medium) | فترة الاحتفاظ (Retention) | الغرض ونطاق الاستخدام |
|---|---|---|---|
| **الطبقة الأولى: التشغيلية (Hot/Operational)** | **GitHub Actions Artifacts** | **90 يوماً** (الحد الأقصى المدعوم في GitHub) | الاسترجاع السريع للحالات الطارئة الأسبوعية والشهرية، مع تشفير GPG AES256 كامل. |
| **الطبقة الثانية: الموسمية (Warm/Season Archive)** | **Offsite Object Storage (Cloudflare R2 / AWS S3)** | **365 يوماً (سنة كاملة / موسم كامل)** | أرشفة شهرية ونسخ ختامية للمواسم. يتم رفع النسخة المشفرة شهرياً إلى مستودع سحابي خارجي منفصل (R2 يوفر 10 جيجابايت مجانية بدون تكاليف نقل بيانات). |
| **الطبقة الثالثة: الدائمة / الامتثال (Cold/Compliance)** | **قرص صلب مشفر خارج الشبكة (Encrypted Offline Disk)** | **3 إلى 5 سنوات** | النسخ الختامية السنوية بعد قفل الموسم (`Season Rollover`) والتقارير المالية المعتمدة للرعاة ولجنة التحكيم. يحتفظ بها مسؤول الـ IT / Super Admin بصيغة مشفرة. |

## 3. دليل تدريب الاستعادة الآمن (Safe Disaster Recovery Drill Runbook)

> [!CAUTION]
> **قاعدة الأمان الذهبية**: لا تقم إطلاقاً بتنفيذ أي تدريب استعادة (Drill) أو اختبار تجريبي على قاعدة بيانات الإنتاج (`Production DB`) أو استخدام سلسلة اتصال الإنتاج أثناء الاختبار. يجب تنفيذ التدريب دائماً على حاوية محلية معزولة أو قاعدة اختبار مخصصة.

### الخطوة الأولى: تنزيل النسخة وفك تشفيرها محلياً
1. توجه إلى تبويب **Actions** في المستودع واختر أحدث تشغيل ناجح لـ **Supabase Database Backup**.
2. نزّل ملف الـ Artifact المشفر (`enactus_backup_YYYYMMDD_HHMMSS.sql.gpg`).
3. فك تشفير الملف في مسار محلي آمن:
```bash
gpg --batch --yes --passphrase "YOUR_BACKUP_PASSPHRASE" \
  --decrypt --output drill_restore.sql enactus_backup_YYYYMMDD_HHMMSS.sql.gpg
```

### الخطوة الثانية: تشغيل حاوية قاعدة بيانات معزولة (Docker Ephemeral Instance)
قم بتشغيل خادم PostgreSQL محلي نظيف على منفذ غير افتراضي (مثلاً `5433` لتجنب أي تداخل مع خوادم محلية أخرى):
```bash
docker run --name pg-drill-isolated \
  -e POSTGRES_DB=drill_test \
  -e POSTGRES_USER=drill_user \
  -e POSTGRES_PASSWORD=drill_pass_local \
  -p 5433:5432 -d postgres:16-alpine

# انتظر 5 ثوانٍ حتى تكتمل جاهزية الخادم
sleep 5
```

### الخطوة الثالثة: استعادة النسخة داخل البيئة المعزولة
```bash
# تنفيذ الاستعادة في قاعدة البيانات المعزولة
PGPASSWORD=drill_pass_local psql -h localhost -p 5433 -U drill_user -d drill_test -f drill_restore.sql
```

### الخطوة الرابعة: تدقيق سلامة الجداول والبيانات المستعادة
قم بتنفيذ استعلام الفحص للتأكد من وجود الجداول الرئيسية وسلامة الصفوف:
```bash
PGPASSWORD=drill_pass_local psql -h localhost -p 5433 -U drill_user -d drill_test -c "
  SELECT 
    table_name,
    (xpath('/row/cnt/text()', xml_count))[1]::text::int AS row_count
  FROM (
    SELECT 
      table_name, 
      query_to_xml(format('SELECT count(*) AS cnt FROM public.%I', table_name), false, true, '') AS xml_count
    FROM information_schema.tables
    WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
  ) t
  ORDER BY table_name;
"
```
**معايير نجاح التدريب**:
- ظهور كافة الجداول الأساسية: `seasons`, `profiles`, `memberships`, `events`, `event_registrations`, `tasks`, `point_entries`, `partners`, `companies`.
- عدم وجود أي أخطاء في تراكيب الجداول أو المفاتيح الخارجية.

### الخطوة الخامسة: التنظيف الفوري ومحو البيانات غير المشفرة
لحماية الخصوصية ومنع بقاء نسخ SQL غير مشفرة على القرص:
```bash
# حذف ملف الـ SQL غير المشفر
rm -f drill_restore.sql

# إيقاف وإزالة الحاوية المؤقتة وبياناتها
docker stop pg-drill-isolated && docker rm -v pg-drill-isolated
```

## 4. خطة الاسترجاع في حالات الطوارئ القصوى (Emergency Production Recovery)

في حال حدوث كارثة تقنية تتطلب استرجاع قاعدة بيانات الإنتاج بالكامل:

1. **إعلان وضع الطوارئ والصيانة**:
   - فعّل وضع الصيانة في Vercel مؤقتاً لتجميد أي طلبات جديدة من الزوار والأعضاء.
2. **التحقق من سلامة النسخة أولاً**:
   - **إلزامي**: نفّذ الخطوات من 1 إلى 4 في بيئة معزولة للتأكد من سلامة ملف النسخة وعدم تعرضه لأي تلف قبل البدء في استرجاعها على بيئة الإنتاج.
3. **الاسترجاع إلى مشروع Supabase**:
   ```bash
   # استرجاع البيانات إلى قاعدة الإنتاج عبر Session Pooler
   psql "$SUPABASE_DB_URL" < verified_restore.sql
   ```
4. **تدقيق ما بعد الاسترجاع**:
   - تحقق من تفعيل الـ RLS والصلاحيات.
   - تحقق من تسجيل دخول المشرفين والصفحات الرئيسية.
   - إزالة وضع الصيانة وإعادة توجيه حركة المرور إلى المنصة.
